Работа с Issues — это фундамент организации задач в любом проекте на **GitHub**. Если **Pull Request** — это «как» вы делаете код, то Issue — это «что» и «почему» вам нужно сделать. Это не просто баг-трекер, а центральное место, где зарождается, обсуждается и отслеживается работа.

Вот полное руководство: от создания первой задачи до построения рабочего процесса.

### 📌 Что такое Issue и зачем он нужен

**Issue** — это базовая единица отслеживаемой работы в репозитории **GitHub**. Это может быть баг, запрос на новую функцию, вопрос или просто задача. Каждый **Issue** получает **постоянный уникальный номер** (например, `#42`), который никогда не меняется. Именно эта нумерация позволяет надежно ссылаться на задачи из кода, коммитов и PR спустя годы.

**Основные типы Issue:**
- **Bug (Ошибка):** «Кнопка входа не работает в Safari» (Safari - это просто пример).
- **Feature Request (Запрос функции):** «Добавить темную тему в настройки».
- **Task / Discussion (Задача/Обсуждение):** «Стоит ли нам отказаться от поддержки Node 16?».

### ✍️ Как создать хороший Issue на примере приложения, плохо работающего в браезере Safari 17

Создать **Issue** просто: перейдите на вкладку **Issues** в репозитории и нажмите **New issue**. Гораздо важнее — правильно его оформить, чтобы исполнитель не гадал, чего вы хотите.

**Ключевые элементы формы создания:**

| Поле | Что это и зачем |
|---|---|
| **Title (Заголовок)** | Краткая и точная суть. Плохо: «Ошибка». Хорошо: «Кнопка Login не реагирует на клик в Safari 17». |
| **Description (Описание)** | Самая важная часть. Здесь вы объясняете **контекст** и **ожидаемый результат**. |
| **Assignees (Исполнители)** | Кому поручена задача (до 10 человек). Можно назначить себя, чтобы показать, что вы взялись за работу. |
| **Labels (Метки)** | Цветные теги для категоризации: `bug`, `enhancement`, `documentation`, `good first issue`, `priority: high` и т.д.. |
| **Milestone (Веха)** | Привязка к конкретному релизу или сроку (например, `v2.0`, `Q3 cleanup`). Помогает понять, в какую версию попадет исправление. |

#### 🧠 Что писать в описании (Description)

Описание поддерживает Markdown, поэтому используйте заголовки, списки и блоки кода. Для разных типов Issue есть свои обязательные блоки.

**Для бага (Bug Report)** — это спасение для разработчика:
```markdown
### Шаги для воспроизведения
1. Открыть главную страницу в Safari.
2. Нажать на кнопку "Войти".
3. ...

### Ожидаемое поведение
Открывается модальное окно входа.

### Фактическое поведение
Кнопка визуально нажимается, но ничего не происходит. В консоли ошибка `Uncaught TypeError`.

### Окружение
- OS: macOS 14.5
- Browser: Safari 17.5
```

**Для запроса функции (Feature Request):**
```markdown
### Какую проблему это решит?
Сейчас нельзя работать ночью, глаза устают от светлой темы.

### Что должно делать?
Добавить переключатель "Темная тема" в настройках профиля.
```

#### 📋 Шаблоны Issue (Issue Templates)

Чтобы не заставлять людей каждый раз вспоминать структуру, в репозитории можно создать шаблоны. Они лежат в папке `.github/ISSUE_TEMPLATE/`. При нажатии «New issue» пользователю будет предложено выбрать шаблон (например, «Bug report» или «Feature request»), и форма уже будет предзаполнена нужными полями и метками.

### 🔗 Связка Issue и Pull Request: магия ключевых слов

Это главная суперсила Issues. Вам не нужно закрывать Issue вручную. Если в описании **Pull Request** (или в сообщении коммита) написать специальное ключевое слово и номер Issue, GitHub сделает всё сам.

**Как это работает:**
В описании PR вы пишете:
> `Closes #42`

Или:
> `Fixes #42`

Когда этот PR будет **слит в основную ветку** (default branch), Issue с номером 42 **автоматически закроется**.

**Поддерживаемые ключевые слова (регистр не важен):**
`close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`.

**Важные нюансы:**
- Работает только при слиянии в **ветку по умолчанию** (обычно `main`). Если PR нацелен на другую ветку, магия не сработает.
- Один PR может закрыть несколько Issues: `Closes #42, closes #43`.
- Можно ссылаться на Issues из другого репозитория: `Fixes octo-org/other-repo#100`.

Связь отображается в обоих направлениях: в Issue появляется запись о том, что её исправляет такой-то PR, а в PR — ссылка на Issue. Это дает полную картину.

### 🗂️ Управление работой: Projects, подзадачи и чек-листы

Когда Issues становится много, на помощь приходят инструменты визуализации.

- **Task Lists (Чек-листы):** Внутри одного Issue можно создать интерактивный список задач. GitHub покажет прогресс-бар, и это отлично подходит для разбивки большой задачи на шаги.
  ```markdown
  - [x] Добавить переключатель темы
  - [ ] Сохранять выбор в localStorage
  - [ ] Учитывать системную настройку `prefers-color-scheme`
  ```

- **Sub-issues (Подзадачи):** Более мощный инструмент. Вы можете сделать один Issue «родительским», а другие — его «детьми». Это позволяет видеть общий прогресс по большой эпической задаче, не теряя деталей.

- **Projects (Проекты):** Это отдельный уровень планирования. Проект собирает Issues и PR из одного или нескольких репозиториев в **таблицы, доски (Kanban) или дорожные карты**. Вы можете создать проект «Спринт 5» и перетаскивать туда задачи, отслеживая их статус (Todo, In Progress, Done).

### 💬 Работа с чужими Issues и этикет

- **Комментирование:** В Issue можно вести обсуждение. Используйте `@username`, чтобы привлечь внимание конкретного человека к вопросу.
- **Кросс-ссылки:** Упоминание `#123` в любом месте (в Issue, PR, комментарии) автоматически создаст ссылку на Issue или PR с этим номером. Это лучший способ показать, что одна задача связана с другой или блокирует её.
- **Реакции:** Используйте эмодзи (👍, 🎉, 👀) для быстрой обратной связи без создания лишних комментариев.
- **Закрытие:** Если Issue больше не актуален (например, проблема решилась сама или это дубликат), его можно закрыть вручную, указав причину (Closed as not planned / duplicate). Но самый правильный путь — через слияние PR с ключевым словом.

### 💎 Итог: минимальный рабочий процесс

1.  **Заметили проблему или придумали идею** → Создаете Issue с четким заголовком и описанием (шаги для бага, ожидаемое поведение).
2.  **Решили заняться** → Назначаете себя исполнителем (Assignee) и ставите метку `in progress` (если такая есть).
3.  **Начинаете работу** → Создаете ветку (можно прямо из Issue на GitHub, тогда связь установится автоматически).
4.  **Сделали** → Открываете Pull Request и в его описании пишете `Closes #<номер вашего Issue>`.
5.  **Ревью и слияние** → Коллеги одобряют PR, он вливается в `main`, а Issue **автоматически закрывается**.
