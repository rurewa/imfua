# Индексы в базах данных: подробное руководство

Индекс — это **отдельная структура данных**, которая ускоряет поиск строк в таблице. Без индекса СУБД просматривает **все** строки (full table scan). С индексом — прыгает сразу к нужным.

Разберём на примере вашей базы `alias_db` (таблицы `customers`, `orders`, `employees`).

---

## 🔹 1. Как это работает физически (InnoDB)

### B-дерево (B-Tree)

Индекс в InnoDB — это **сбалансированное дерево поиска** (B+Tree). Оно хранит **отсортированные** значения столбца + указатели на строки.

```
            [50]
           /    \
      [20]        [80]
     /   \       /   \
  [10] [30]   [60] [90]
```

Поиск значения `80`:
- Без индекса: просмотр всех строк (N шагов).
- С индексом: 3 шага (корень → узел → лист).

**Сложность:** O(log n) вместо O(n). Для 1 000 000 строк это ~20 шагов вместо 1 000 000.

### Что хранится в листьях

- **Некластеризованный индекс:** значение столбца + **первичный ключ** строки.
- **Кластеризованный индекс (InnoDB):** сама таблица физически отсортирована по первичному ключу. Листья — это строки целиком.

## 🔹 2. Кластеризованный vs некластеризованный

### Кластеризованный индекс (Clustered Index)

В InnoDB **первичный ключ — это кластеризованный индекс**. Таблица хранится в файле `.ibd` **отсортированной по PK**.

```sql
CREATE TABLE customers (
    id INT AUTO_INCREMENT PRIMARY KEY,  -- кластеризованный индекс
    name VARCHAR(100),
    ...
);
```

**Что это значит:**
- Строки физически лежат в порядке `id`.
- Поиск по `id` — самый быстрый (прямое попадание).
- В таблице может быть **только один** кластеризованный индекс.

### Некластеризованный индекс (Secondary Index)

Любой `CREATE INDEX` создаёт **вторичный** индекс — отдельную структуру с копией значений столбца и указателем на PK.

```sql
CREATE INDEX idx_city ON customers(city);
```

Теперь есть:
- Кластеризованный по `id` (сама таблица).
- Некластеризованный по `city` (отдельное B-дерево).

**Как работает запрос:**

```sql
SELECT * FROM customers WHERE city = 'Москва';
```

1. Ищет `'Москва'` в `idx_city` → находит PK (например, 1, 3).
2. По PK идёт в кластеризованный индекс (таблицу) → достаёт строки.

Это **двойной поиск** (index lookup + row lookup). Если строк много, может быть медленнее, чем ожидается.

## 🔹 3. Составные индексы: порядок столбцов критичен

```sql
CREATE INDEX idx_city_name ON customers(city, name);
```

Это индекс по **паре** `(city, name)`. Он работает для:

```sql
-- ✅ Использует индекс (city — первый столбец)
WHERE city = 'Москва';

-- ✅ Использует индекс (city + name)
WHERE city = 'Москва' AND name = 'Иван Иванов';

-- ✅ Использует индекс частично (только city)
WHERE city = 'Москва' AND name LIKE 'И%';

-- ❌ НЕ использует индекс (name — не первый столбец)
WHERE name = 'Иван Иванов';
```

**Правило левого префикса:** индекс `(A, B, C)` работает для `A`, `(A, B)`, `(A, B, C)`, но **не** для `B`, `(B, C)`, `C`.

### Как выбрать порядок столбцов

1. **Столбец с наибольшей селективностью** (больше уникальных значений) — первым. `city` (5 городов) vs `email` (100 000 уникальных) — `email` селективнее.
2. **Столбцы из `WHERE`** — в начало.
3. **Столбцы из `ORDER BY`** — в конец (если не конфликтуют).

**Пример:**

```sql
-- Частый запрос:
SELECT * FROM orders
WHERE customer_id = 1 AND status = 'paid'
ORDER BY order_date DESC;

-- Оптимальный индекс:
CREATE INDEX idx_customer_status_date ON orders(customer_id, status, order_date);
```

## 🔹 4. Покрывающий индекс (Covering Index)

Если индекс содержит **все** столбцы, которые нужны запросу, СУБД **не обращается к таблице** вообще. Это называется **Index-Only Scan**.

```sql
CREATE INDEX idx_city_name ON customers(city, name);

-- Запрос:
SELECT name FROM customers WHERE city = 'Москва';
```

Индекс `(city, name)` содержит и `city` (для `WHERE`), и `name` (для `SELECT`). MySQL читает только индекс — таблица не нужна.

**Проверить в `EXPLAIN`:** столбец `Extra` содержит `Using index`.

**Когда это полезно:**
- Частые запросы с фиксированным набором столбцов.
- Большие таблицы, где чтение строк дорого.

**Минус:** индекс занимает больше места. Не стоит делать «покрывающий на всё».

---

## 🔹 5. Когда индексы **помогают**

| Ситуация | Пример |
|----------|--------|
| **`WHERE` по столбцу** | `WHERE city = 'Москва'` |
| **`JOIN` по столбцу** | `ON c.id = o.customer_id` (внешний ключ) |
| **`ORDER BY`** | `ORDER BY amount DESC` (если индекс по `amount`) |
| **`GROUP BY`** | `GROUP BY customer_id` |
| **`UNIQUE` / `PRIMARY KEY`** | Проверка уникальности |
| **`LIKE 'prefix%'`** | `LIKE 'Иван%'` (только префикс!) |
| **`MIN` / `MAX`** | Если индекс по столбцу |

---

## 🔹 6. Когда индексы **вредят**

| Ситуация | Почему |
|----------|--------|
| **Маленькие таблицы** (< 1000 строк) | Full scan быстрее, чем индекс + row lookup |
| **Низкая селективность** | `INDEX(gender)` — 2 значения, бесполезно |
| **Частые `INSERT` / `UPDATE` / `DELETE`** | Каждое изменение обновляет все индексы → замедление |
| **`LIKE '%суффикс'`** | Индекс не работает (только префикс) |
| **`WHERE` с функцией** | `WHERE YEAR(order_date) = 2026` — индекс не используется |
| **`OR` по разным столбцам** | `WHERE city = 'Москва' OR amount > 1000` — может не использовать индекс |
| **Много индексов на таблице** | Каждый `INSERT` обновляет все → замедление записи |

**Правило:** индекс ускоряет **чтение**, но замедляет **запись**. Не индексируйте «на всякий случай».

## 🔹 7. `EXPLAIN`: как проверить, работает ли индекс

```sql
EXPLAIN SELECT * FROM orders WHERE amount > 1000;
```

**Ключевые столбцы:**

| Столбец | Что означает |
|---------|--------------|
| `type` | Тип доступа: `ALL` (full scan — плохо), `index` (полный индекс — средне), `range` (диапазон — хорошо), `ref` (точечный — хорошо), `eq_ref` (уникальный — отлично), `const` (константа — идеально) |
| `key` | Какой индекс используется (`NULL` — индекса нет) |
| `rows` | Сколько строк предполагается просмотреть |
| `Extra` | `Using index` (покрывающий), `Using temporary` (временная таблица — плохо), `Using filesort` (сортировка — плохо) |

### Пример: до и после индекса

**Без индекса:**

```sql
EXPLAIN SELECT * FROM orders WHERE amount > 1000;
```

```
+----+-------------+--------+------+---------------+------+---------+------+------+-------------+
| id | select_type | table  | type | possible_keys | key  | key_len | ref  | rows | Extra       |
+----+-------------+--------+------+---------------+------+---------+------+------+-------------+
|  1 | SIMPLE      | orders | ALL  | NULL          | NULL | NULL    | NULL |    6 | Using where |
+----+-------------+--------+------+---------------+------+---------+------+------+-------------+
```

`type: ALL` — full scan. 6 строк — ещё не страшно. Но на 1 000 000 строк — катастрофа.

**С индексом:**

```sql
CREATE INDEX idx_amount ON orders(amount);
EXPLAIN SELECT * FROM orders WHERE amount > 1000;
```

```
+----+-------------+--------+-------+---------------+------------+---------+------+------+-------------+
| id | select_type | table  | type  | possible_keys | key        | key_len | ref  | rows | Extra       |
+----+-------------+--------+-------+---------------+------------+---------+------+------+-------------+
|  1 | SIMPLE      | orders | range | idx_amount    | idx_amount | 5       | NULL |    4 | Using where |
+----+-------------+--------+-------+---------------+------------+---------+------+------+-------------+
```

`type: range`, `key: idx_amount` — индекс используется. `rows: 4` вместо 6.

## 🔹 8. Практические примеры на вашей базе

### Пример 1: внешний ключ — всегда индексируется

```sql
-- В таблице orders есть:
FOREIGN KEY (customer_id) REFERENCES customers(id)
```

MySQL **автоматически** создаёт индекс на `customer_id`. Проверьте:

```sql
SHOW INDEX FROM orders;
```

Увидите `PRIMARY` (кластеризованный по `id`) и `customer_id` (внешний ключ).

**Зачем:** `JOIN` по `customer_id` ищет строки в `orders` по значению — индекс ускоряет это.

### Пример 2: частый запрос — добавим индекс

```sql
-- Часто ищем заказы по статусу и дате:
SELECT * FROM orders
WHERE status = 'paid' AND order_date > '2026-10-01';

-- Без индекса — full scan.
-- Добавим составной индекс:
CREATE INDEX idx_status_date ON orders(status, order_date);

-- Проверим:
EXPLAIN SELECT * FROM orders WHERE status = 'paid' AND order_date > '2026-10-01';
```

`type: range`, `key: idx_status_date` — работает.

### Пример 3: покрывающий индекс

```sql
-- Часто считаем сумму по клиенту:
SELECT customer_id, SUM(amount) FROM orders GROUP BY customer_id;

-- Индекс только по customer_id:
CREATE INDEX idx_customer ON orders(customer_id);

-- А лучше — покрывающий:
CREATE INDEX idx_customer_amount ON orders(customer_id, amount);
```

Второй индекс содержит и `customer_id`, и `amount` — MySQL может посчитать сумму, не читая таблицу (`Using index`).

### Пример 4: когда индекс НЕ работает

```sql
-- ❌ Функция в WHERE:
SELECT * FROM orders WHERE YEAR(order_date) = 2026;
-- Индекс по order_date не используется.

-- ✅ Перепишем:
SELECT * FROM orders WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01';
-- Индекс работает.
```

```sql
-- ❌ LIKE с суффиксом:
SELECT * FROM customers WHERE name LIKE '%Иван';
-- Индекс не работает.

-- ✅ LIKE с префиксом:
SELECT * FROM customers WHERE name LIKE 'Иван%';
-- Индекс работает.
```

## 🔹 9. Типы индексов в MySQL

| Тип | Когда использовать | Пример |
|-----|-------------------|--------|
| **PRIMARY** | Первичный ключ | `id INT PRIMARY KEY` |
| **UNIQUE** | Уникальность | `email VARCHAR(100) UNIQUE` |
| **INDEX (обычный)** | Ускорение поиска | `CREATE INDEX idx_city ON customers(city)` |
| **FULLTEXT** | Полнотекстовый поиск | `FULLTEXT(name)` — для `MATCH ... AGAINST` |
| **SPATIAL** | Геоданные | `SPATIAL INDEX(geo)` — для `POINT`, `POLYGON` |

**FULLTEXT** — отдельная тема. Работает для `MATCH(col) AGAINST('слово')`, а не для `LIKE '%слово%'`.

## 🔹 10. Управление индексами

### Создать

```sql
-- При создании таблицы:
CREATE TABLE customers (
    ...
    INDEX idx_city (city)
);

-- Или после:
CREATE INDEX idx_city ON customers(city);
CREATE UNIQUE INDEX idx_email ON customers(email);
```

### Посмотреть

```sql
SHOW INDEX FROM customers;
SHOW CREATE TABLE customers\G
```

### Удалить

```sql
DROP INDEX idx_city ON customers;
```

### Переименовать (MySQL 8.0+)

```sql
ALTER TABLE customers RENAME INDEX idx_city TO idx_customer_city;
```

## 🔹 11. Распространённые ошибки

| Ошибка | Почему плохо | Что делать |
|--------|--------------|------------|
| Индекс на всё | Замедляет запись, занимает место | Индексировать только частые запросы |
| Индекс на низкую селективность | Бесполезен | Не создавать (`gender`, `is_active`) |
| Забыть про порядок в составном индексе | `(name, city)` не работает для `WHERE city = ...` | Ставить селективные столбцы первыми |
| `LIKE '%...'` с индексом | Не работает | Использовать `LIKE 'prefix%'` или FULLTEXT |
| Функция в `WHERE` | Индекс не используется | Переписать без функции |
| Слишком много индексов на таблице | Запись замедляется | Оставить только нужные |

## 🔹 12. Как найти «узкие места» в вашей базе

```sql
-- Какие индексы есть:
SHOW INDEX FROM orders;

-- Какие запросы работают медленно:
SELECT * FROM orders WHERE amount > 1000;
EXPLAIN SELECT * FROM orders WHERE amount > 1000;

-- Размер индексов:
SELECT
    TABLE_NAME,
    INDEX_NAME,
    ROUND(SUM(STAT_VALUE * @@innodb_page_size) / 1024 / 1024, 2) AS size_mb
FROM mysql.innodb_index_stats
WHERE STAT_NAME = 'size' AND DATABASE_NAME = 'alias_db'
GROUP BY TABLE_NAME, INDEX_NAME;

-- Или проще (MySQL 8.0):
SELECT
    TABLE_NAME,
    INDEX_NAME,
    ROUND(SUM(STAT_VALUE * @@innodb_page_size) / 1024 / 1024, 2) AS size_mb
FROM mysql.innodb_index_stats
WHERE STAT_NAME = 'size'
  AND DATABASE_NAME = 'alias_db'
GROUP BY TABLE_NAME, INDEX_NAME;
```

## 📌 Итог

| Что важно запомнить об индексах |
|----------------------------------|
| Индекс — это **B-дерево**, ускоряющее поиск с O(n) до O(log n) |
| **Кластеризованный** — сама таблица (PK в InnoDB), **некластеризованный** — отдельная структура |
| **Составной индекс** работает по **левому префиксу**: `(A, B)` — для `A` и `(A, B)`, но не для `B` |
| **Покрывающий индекс** содержит все нужные столбцы → таблица не читается (`Using index`) |
| Индекс ускоряет **чтение**, но замедляет **запись** |
| **`EXPLAIN`** — главный инструмент проверки: `type: ALL` — плохо, `ref` / `range` — хорошо |
| Функции в `WHERE` и `LIKE '%...'` **ломают** индекс |
| Не индексируйте «на всякий случай» — только под частые запросы |

**Практическое задание для вашего контейнера:**

1. Посмотрите `SHOW INDEX FROM orders;` — какие индексы уже есть?
2. Выполните `EXPLAIN SELECT * FROM orders WHERE amount > 1000;` — full scan?
3. Создайте `CREATE INDEX idx_amount ON orders(amount);` и повторите `EXPLAIN`.
4. Сравните `type` и `rows`.
5. Попробуйте `EXPLAIN SELECT * FROM orders WHERE YEAR(order_date) = 2026;` — видите, что индекс не работает? Перепишите запрос.
