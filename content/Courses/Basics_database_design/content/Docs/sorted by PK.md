# Что значит «таблица хранится в `.ibd`-файле, отсортированная по PK»

Это одна из ключевых особенностей InnoDB: **строки таблицы физически лежат в файле не в порядке вставки, а в порядке возрастания первичного ключа**. Разберём, что это значит на практике.

---

## 🔹 1. Что такое `.ibd`-файл

Каждая таблица InnoDB (при `innodb_file_per_table = ON`, что по умолчанию) хранится в **отдельном файле** с расширением `.ibd` — InnoDB Data file.

```shell
docker exec -it mysql_alias ls -la /var/lib/mysql/alias_db/
```

Вы увидите:

```
customers.ibd
orders.ibd
employees.ibd
```

Внутри каждого `.ibd` — **страницы по 16 КБ**. На этих страницах лежат строки таблицы, индексы и служебные данные.

---

## 🔹 2. Что значит «отсортированы по PK»

### Обычная таблица (heap-organized)

В некоторых СУБД (например, PostgreSQL) строки лежат в файле **в порядке вставки**. Добавили три строки — они идут друг за другом:

```
Страница 1: [Иван] [Мария] [Пётр]   ← порядок вставки
```

Поиск по `id` без индекса → нужно просмотреть **все** страницы.

### InnoDB (clustered index)

InnoDB хранит таблицу как **B+Tree, упорядоченное по первичному ключу**. Строки на страницах физически отсортированы по `id`:

```
Страница 1: [id=1 Иван] [id=2 Мария] [id=3 Пётр]
Страница 2: [id=4 Ольга] [id=5 Алексей] ...
```

**Что это даёт:**

- Поиск по `id` — это бинарный поиск по дереву: O(log n), а не O(n).
- Диапазонные запросы (`WHERE id BETWEEN 10 AND 20`) читают **непрерывный участок** страниц — быстро.
- `ORDER BY id` не требует сортировки — данные уже в этом порядке.

---

## 🔹 3. Наглядный пример

Представьте, что вы вставляете строки **в случайном порядке**:

```sql
INSERT INTO customers (id, name) VALUES (5, 'Алексей');
INSERT INTO customers (id, name) VALUES (1, 'Иван');
INSERT INTO customers (id, name) VALUES (3, 'Мария');
INSERT INTO customers (id, name) VALUES (2, 'Пётр');
INSERT INTO customers (id, name) VALUES (4, 'Ольга');
```

**В PostgreSQL** (heap) строки лягут в порядке вставки:

```
[5 Алексей] [1 Иван] [3 Мария] [2 Пётр] [4 Ольга]
```

**В InnoDB** строки будут **пересортированы** по `id`:

```
[1 Иван] [2 Пётр] [3 Мария] [4 Ольга] [5 Алексей]
```

Физически на диске — именно так. Не важно, в каком порядке вы вставляли.

---

## 🔹 4. Как это проверить

### 4.1. Косвенно — через `ORDER BY` без сортировки

```sql
EXPLAIN SELECT * FROM customers ORDER BY id;
```

В столбце `Extra` **не будет** `Using filesort` — потому что данные уже отсортированы. MySQL читает их в порядке кластеризованного индекса.

А теперь:

```sql
EXPLAIN SELECT * FROM customers ORDER BY name;
```

Скорее всего, увидите `Using filesort` — потому что по `name` данные **не** отсортированы, нужна дополнительная сортировка.

### 4.2. Через физическое расположение (частично)

```sql
SELECT id, name FROM customers;
```

Результат **обычно** выводится в порядке `id` — потому что MySQL читает кластеризованный индекс по порядку. Но это **не гарантировано** стандартом: без `ORDER BY` порядок может измениться (например, при `JOIN` или `GROUP BY`).

### 4.3. Через `innodb_ruby` или `innodb_space` (продвинуто)

Существуют утилиты, которые читают `.ibd`-файл напрямую и показывают физическое расположение страниц. Но для учебных целей это избыточно.

## 🔹 5. Что это значит на практике

| Ситуация | Поведение InnoDB |
|----------|------------------|
| `WHERE id = 42` | Быстро: бинарный поиск по дереву |
| `WHERE id BETWEEN 10 AND 20` | Быстро: читается непрерывный участок |
| `ORDER BY id` | Бесплатно: данные уже в этом порядке |
| `ORDER BY name` | Медленно: нужна сортировка (`Using filesort`) |
| Вставка `id = 100` в таблицу с `id` 1..99 | В конец — просто |
| Вставка `id = 50` в таблицу с `id` 1..99 | **В середину** — страница может разделиться (page split) |

**Последний пункт — важный:** если PK — `AUTO_INCREMENT`, вставка всегда в конец (быстро). Если PK — случайный (`UUID`), вставка идёт в середину дерева → страницы постоянно разделяются → **замедление вставки** и **фрагментация**.

Именно поэтому **`AUTO_INCREMENT` предпочтительнее `UUID`** для первичного ключа в InnoDB.

---

## 🔹 6. А если первичного ключа нет?

InnoDB **всегда** нужен кластеризованный индекс. Если вы не объявили `PRIMARY KEY`, InnoDB:

1. Ищет первый `UNIQUE NOT NULL` индекс → делает его кластеризованным.
2. Если такого нет — создаёт **скрытый** кластеризованный индекс по внутреннему `ROW_ID` (6 байт, автоинкремент).

То есть таблица **всё равно** отсортирована — либо по вашему PK, либо по скрытому `ROW_ID`.

---

## 🔹 7. Сравнение с другими СУБД

| СУБД | Как хранит таблицу |
|------|---------------------|
| **InnoDB (MySQL)** | Кластеризованный индекс по PK → строки **отсортированы** |
| **MyISAM (MySQL)** | Heap → строки в порядке вставки |
| **PostgreSQL** | Heap → строки в порядке вставки (но есть `CLUSTER` для пересортировки) |
| **SQL Server** | Кластеризованный индекс (если объявлен) или heap |

---

## 📌 Итог

**«Таблица хранится в `.ibd`-файле, отсортированная по PK»** означает:

1. Физически на диске строки лежат **в порядке возрастания первичного ключа**, а не в порядке вставки.
2. Это следствие того, что InnoDB использует **кластеризованный индекс**: таблица и есть B+Tree, упорядоченное по PK.
3. Поиск по PK — быстрый (O(log n)), диапазонные запросы — быстрые, `ORDER BY PK` — бесплатный.
4. Вставка в середину (например, случайный `UUID`) — медленнее, чем в конец (`AUTO_INCREMENT`).

**Практический вывод:** если хотите быструю вставку — используйте `AUTO_INCREMENT` PK. Если хотите быстрый поиск по диапазону PK — кластеризованный индекс уже даёт это «из коробки».

# Да, PK — это аббревиатура от PRIMARY KEY

**PK** = **P**rimary **K**ey (первичный ключ).

Это стандартное сокращение, которое используется в документации, схемах БД, инструментах проектирования (ERwin, dbdiagram.io, DBeaver) и в общении разработчиков.

---

## 🔹 Другие распространённые сокращения

| Сокращение | Расшифровка | Значение |
|------------|-------------|----------|
| **PK** | Primary Key | Первичный ключ |
| **FK** | Foreign Key | Внешний ключ |
| **UK** | Unique Key | Уникальный ключ (ограничение `UNIQUE`) |
| **CK** | Check Constraint | Проверочное ограничение (`CHECK`) |
| **NN** | Not Null | Ограничение `NOT NULL` |
| **AI** | Auto Increment | Автоинкремент (`AUTO_INCREMENT`) |
| **IX** / **IDX** | Index | Индекс |

---

## 🔹 Где вы это увидите

В **ER-диаграммах** (например, в нотации «воронья лапка»):

```
┌─────────────────┐
│   customers     │
├─────────────────┤
│ id    INT  PK   │  ← PK = первичный ключ
│ name  VARCHAR   │
│ email VARCHAR UK│  ← UK = уникальный
└─────────────────┘
```

В **выводе `SHOW INDEX`** из MySQL:

```sql
SHOW INDEX FROM customers;
```

| Key_name | Column_name | Non_unique |
|----------|-------------|------------|
| PRIMARY | id | 0 |

`PRIMARY` — это и есть кластеризованный индекс по PK.

В **`EXPLAIN`**:

```
| key | PRIMARY |
```

Если `key = PRIMARY`, значит, используется кластеризованный индекс по первичному ключу.

---

## 📌 Итог

**PK = PRIMARY KEY.** Да, это простое сокращение. В контексте InnoDB «отсортированы по PK» означает «отсортированы по первичному ключу».
