## EXPLAIN

`EXPLAIN` — это, пожалуй, самый важный инструмент для разработчика или администратора, работающего с базами данных. Если индексы — это «словарь» для быстрого поиска, то `EXPLAIN` — это «рентген», который показывает, *как именно* MySQL собирается выполнять ваш запрос, и почему он может работать медленно.

Давайте разберём его подробно, шаг за шагом.

---

### 🔍 1. Что такое EXPLAIN и зачем он нужен?

Команда `EXPLAIN` (или её синоним `DESCRIBE`) показывает **план выполнения** SQL-запроса. Проще говоря, она отвечает на вопрос: «Что MySQL собирается делать, чтобы получить результат?».

**Зачем это нужно:**
*   **Найти причину медленного запроса:** Вы видите, что запрос выполняется 2 секунды. `EXPLAIN` покажет, что MySQL просматривает всю таблицу (full scan), а не использует индекс.
*   **Проверить, работает ли индекс:** Вы создали индекс, но запрос не ускорился. `EXPLAIN` покажет, задействован ли он (`key`) или нет.
*   **Понять, как СУБД интерпретирует ваш код:** Иногда запрос написан так, что СУБД не может применить индекс (например, из-за функции в `WHERE`).

### 📊 2. Как читать вывод EXPLAIN: основные столбцы

`EXPLAIN` возвращает таблицу, где каждая строка — это информация об одной таблице, участвующей в запросе. Вот ключевые столбцы:

| Столбец | Что означает | На что смотреть |
| :--- | :--- | :--- |
| **`id`** | Порядковый номер `SELECT` в запросе. | Помогает понять порядок выполнения для подзапросов или `UNION`. |
| **`select_type`** | Тип запроса: `SIMPLE`, `PRIMARY`, `SUBQUERY`, `DERIVED` и т.д. | Показывает, является ли запрос простым или содержит подзапросы. |
| **`table`** | Имя таблицы, к которой применяется строка плана. | — |
| **`partitions`** | Какие партиции будут затронуты (если таблица партиционирована). | `NULL` означает, что партиционирования нет. |
| **`type`** | **Тип доступа (Join Type).** Самый важный столбец для оценки производительности. | **Чем «выше» тип, тем лучше.** Подробнее — ниже. |
| **`possible_keys`** | Индексы, которые *могли бы* быть использованы для поиска строк. | `NULL` — индексов, подходящих для этого запроса, нет. |
| **`key`** | **Фактически выбранный индекс.** | `NULL` — **индекс не используется**. Это главный признак проблемы. |
| **`key_len`** | Длина использованного ключа в байтах. | Помогает понять, какая часть составного индекса задействована. |
| **`ref`** | Столбцы или константы, которые сравниваются с индексом (`key`). | — |
| **`rows`** | **Оценка количества строк, которые придётся просмотреть.** | **Крайне важно.** Чем меньше `rows`, тем быстрее запрос. Сравнивайте это значение до и после добавления индекса. |
| **`filtered`** | Процент строк, которые останутся после фильтрации по условию `WHERE`. | `100.00` — идеально, все строки прошли фильтр. |
| **`Extra`** | **Дополнительная важная информация.** | `Using index` (хорошо), `Using filesort` / `Using temporary` (плохо). Подробнее — ниже. |

### 🚦 3. Ключевой столбец `type`: от лучшего к худшему

Этот столбец показывает, как MySQL будет искать строки. Вот иерархия типов от самого эффективного к самому медленному:

1.  **`system`**: Таблица состоит из одной строки. Самый быстрый тип.
2.  **`const`**: Поиск по первичному ключу или уникальному индексу с константным значением (`WHERE id = 1`). Возвращает максимум одну строку.
3.  **`eq_ref`**: Одна строка из этой таблицы читается для каждой строки из предыдущей таблицы. Используется в `JOIN` по первичному/уникальному ключу.
4.  **`ref`**: Поиск по неуникальному индексу (`WHERE city = 'Москва'`). Может вернуть несколько строк.
5.  **`range`**: Поиск по диапазону значений с использованием индекса (`WHERE amount > 1000`, `BETWEEN`, `IN`). **Это хороший результат для индексного поиска.**
6.  **`index`**: Полный просмотр **всего индекса** (а не таблицы). Может быть быстрее `ALL`, но всё равно медленно, так как читается весь индекс.
7.  **`ALL`**: **Полный просмотр таблицы (Full Table Scan).** Самый плохой тип, означает, что индекс не используется и MySQL перебирает все строки.

> **Правило:** Если вы видите `type: ALL` на большой таблице, это главный кандидат на оптимизацию.

### 🧩 4. Ключевой столбец `Extra`: что он скрывает

Здесь содержится много полезной информации о том, как MySQL обрабатывает запрос после доступа к таблице.

*   ✅ **`Using index`**: **Отличный признак!** Означает, что запрос может быть выполнен только с использованием индекса, без чтения самой таблицы («покрывающий индекс»). Это самый быстрый вариант.
*   ⚠️ **`Using where`**: Фильтрация строк происходит после их чтения из таблицы или индекса. Это нормально, но указывает на то, что не весь `WHERE` был покрыт индексом.
*   ⚠️ **`Using filesort`**: MySQL вынужден выполнять **дополнительную сортировку** строк, так как индекс не обеспечивает нужный порядок для `ORDER BY`. Это消耗ает ресурсы CPU и память.
*   ❌ **`Using temporary`**: MySQL создаёт **временную таблицу** для выполнения запроса (часто при `GROUP BY` или `DISTINCT`). Это медленно и ресурсоёмко.

### 🕵️‍♂️ 5. Почему индекс «не работает»: типичные примеры

`EXPLAIN` поможет это увидеть. Вот несколько ситуаций, когда индекс, скорее всего, не будет использован (`key: NULL`, `type: ALL`).

#### Пример 1: Функция в `WHERE`

```sql
-- ❌ Индекс по order_date не будет использован
EXPLAIN SELECT * FROM orders WHERE YEAR(order_date) = 2026;
```
MySQL не может применить индекс, потому что функция `YEAR()` вычисляется для каждой строки.
**Решение:** Переписать условие, чтобы столбец был «чистым».
```sql
-- ✅ Индекс будет использован
EXPLAIN SELECT * FROM orders
WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01';
```

#### Пример 2: `LIKE` с ведущим `%`

```sql
-- ❌ Индекс не используется
EXPLAIN SELECT * FROM customers WHERE name LIKE '%ван';
```
Индекс (B-дерево) хранит значения в отсортированном виде, и поиск по префиксу (`LIKE 'Иван%'`) работает, а по суффиксу — нет.

#### Пример 3: `OR` с неиндексированным столбцом

```sql
-- ❌ Если по столбцу status нет индекса, type будет ALL
EXPLAIN SELECT * FROM orders WHERE amount > 1000 OR status = 'new';
```
Если хотя бы одна часть условия `OR` не может быть эффективно обработана индексом, MySQL может выбрать полный перебор таблицы.

### 🚀 6. Продвинутые возможности: `EXPLAIN ANALYZE` и `FORMAT=JSON`

*   **`EXPLAIN ANALYZE`** (доступно с MySQL 8.0.18): Выполняет запрос и показывает **реальное время** выполнения каждого шага плана, а не только оценку. Это помогает найти «узкое место», которое оптимизатор недооценил.
    ```sql
    EXPLAIN ANALYZE SELECT * FROM orders WHERE amount > 1000;
    ```
*   **`EXPLAIN FORMAT=JSON`**: Выводит план в формате JSON, который содержит больше деталей (например, стоимость операций, используемые столбцы) и удобен для автоматической обработки.
    ```sql
    EXPLAIN FORMAT=JSON SELECT * FROM orders WHERE amount > 1000\G
    ```

### 💎 Итог

`EXPLAIN` — это не просто команда, а обязательный шаг в оптимизации любого запроса. Он превращает написание SQL из «угадывания» в инженерную работу.

**Ваша шпаргалка для быстрой диагностики:**
1.  **Смотрите на `type`:** `ALL` — плохо, `range` / `ref` — хорошо.
2.  **Смотрите на `key`:** `NULL` — индекс не используется.
3.  **Смотрите на `rows`:** Чем меньше, тем лучше. Сравнивайте до и после.
4.  **Смотрите на `Extra`:** `Using index` — отлично, `Using filesort` / `Using temporary` — требует внимания.

Попробуйте применить `EXPLAIN` к вашим запросам из руководства по индексам. Сравните план для `SELECT * FROM orders WHERE amount > 1000` до и после создания индекса `idx_amount`. Вы увидите, как `type` изменится с `ALL` на `range`, а `rows` уменьшится. Это и есть магия индексов, которую `EXPLAIN` делает видимой.
