# Лабораторная работа: Pull Request (PR)

## 🎯 Цель работы

Освоить базовый сценарий командной работы с Git через платформу хостинга (GitHub): создать форк, внести изменения в отдельной ветке, оформить Pull Request, пройти ревью и выполнить слияние в основную ветку.

## 📋 Требования

- Установлен Git.
- Есть аккаунт на GitHub.
- Настроены `user.name` и `user.email` в Git:
  ```bash
  git config --global user.name "Ваше Имя"
  git config --global user.email "you@example.com"
  ```

## 📖 Теоретическая справка

**Pull Request (PR)** — это механизм платформ хостинга Git (GitHub, GitLab и др.), который позволяет предложить изменения из вашей ветки в основную ветку проекта и провести их ревью перед слиянием. В GitLab аналог PR называется **Merge Request (MR)**.

Вместо прямого изменения главной ветки вы создаёте отдельную ветку, вносите правки и через PR предлагаете команде посмотреть их и, если всё хорошо, добавить в проект.

**Зачем нужен PR?**

- **Повышает качество кода**: другие разработчики проверяют изменения (**Code Review**), находят ошибки, предлагают улучшения.
- **Сохраняет историю**: внутри PR фиксируются комментарии, замечания и исправления — позже можно понять, *почему* было принято то или иное решение.
- **Снижает риски**: изменения не попадают в основную ветку автоматически, а проходят проверку и тестирование.
- **Автоматизирует проверки**: к PR можно подключить тесты, линтеры и проверки безопасности.

> **Примечание.** В этой лабораторной мы имитируем open-source-сценарий и используем **форки**. В реальной команде с общим репозиторием участников обычно добавляют как collaborator, и тогда форк не нужен — достаточно создать ветку в общем репозитории.

## 🧪 Сценарий выполнения

**Роли:** тимлид (владелец репозитория) и участники команды (студенты).

**Подготовка (тимлид):**

1. Создаёт новый **публичный** репозиторий на GitHub с файлом `README.md`.
2. Заполняет `README.md` произвольной информацией (например, описанием проекта) и делает push в `main`.

**Работа участников команды:**

### Шаг 1. Форк (Fork)

Поскольку у участников нет прав на редактирование чужого репозитория, они нажимают кнопку **Fork** в репозитории тимлида. Это создаёт личную копию репозитория в аккаунте участника.

### Шаг 2. Клонирование и создание ветки

Участник клонирует **свой форк** на компьютер, переходит в папку репозитория и создаёт новую ветку для правок:

```bash
git clone https://github.com/<ваш-username>/<имя-репозитория>.git
cd <имя-репозитория>
git checkout -b fix-typo-in-readme
```

Ветка — это изолированная рабочая среда, где изменения не затрагивают основную ветку.

### Шаг 3. Внесение изменений и push

Участник исправляет опечатку в файле `README.md`, сохраняет его, делает коммит и отправляет ветку на GitHub:

```bash
git add README.md
git commit -m "Исправлена опечатка в разделе Installation"
git push origin fix-typo-in-readme
```

### Шаг 4. Создание Pull Request

После push GitHub предложит создать Pull Request (обычно появляется кнопка **Compare & pull request**). При создании PR нужно явно указать:

- **base repository** — исходный репозиторий тимлида;
- **base branch** — `main`;
- **head repository** — ваш форк;
- **compare branch** — `fix-typo-in-readme`.

Заполните два ключевых поля:

- **Заголовок (Title)**: кратко описывает суть, например «Исправлена опечатка в README».
- **Описание (Description)**: подробно объясняет, *что* и *зачем* вы сделали.

### Шаг 5. Ревью и обсуждение

Теперь PR виден тимлиду. Он открывает вкладку **Files changed**, чтобы построчно увидеть правки участников (это называется **diff**), и оставляет комментарии под конкретными строками или пишет общее мнение в обсуждении.

При необходимости участник вносит правки в ту же ветку — они автоматически попадут в PR.

### Шаг 6. Слияние (Merge)

Если правки одобрены и все автоматические проверки пройдены, тимлид нажимает **Merge pull request**. Изменения участников вливаются в основную ветку оригинального проекта, и они становятся контрибьюторами.

## 💡 Полезные нюансы

- **Draft Pull Request**: если работа ещё не завершена, но хочется показать черновик или получить ранний отзыв, создайте **Draft PR**. Такой запрос нельзя случайно слить, и он помечен как «в работе».
- **Защита веток (Branch Protection)**: в серьёзных проектах настройки репозитория часто запрещают прямой push в `main`. Единственный способ добавить код — создать PR и пройти ревью.

## 📦 Ожидаемый результат

По итогам лабораторной у каждого участника:

- есть форк репозитория тимлида;
- создана отдельная ветка с изменениями;
- оформлен Pull Request с осмысленным заголовком и описанием;
- пройдено ревью (получен хотя бы один комментарий или одобрение);
- PR слит в `main` исходного репозитория.

## ✅ Критерии оценки

| Критерий | Баллы |
|---|---|
| Создан форк и склонирован локально | 1 |
| Создана отдельная ветка с осмысленным названием | 1 |
| Сделан коммит с корректным сообщением | 1 |
| Оформлен Pull Request (заголовок + описание) | 2 |
| Проведено ревью (оставлен комментарий или одобрение) | 2 |
| PR успешно слит в `main` | 2 |
| Участник числится контрибьютором репозитория | 1 |
